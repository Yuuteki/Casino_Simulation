# Casino Simulation 技术架构 v0.1

## 0. 2026-07-12 已确认更新

以下内容来自 `CODEX_HANDOFF_2026-07-12.md`，优先于本文旧段落：

- 好友联机的上层单位是最多六名真人玩家的持久派对，而不是绑定单张桌的临时房间。
- 派对成员、Host、连接、外观数据和已确认官方筹码余额在切换玩法时保留；当前玩法的 round state、shoe/deck、bets、timers 和临时数据不得跨玩法携带。
- AI 不占用派对成员槽位，只填充当前桌面空位。
- 玩家可在非满员派对中途加入；加入不会重置、回滚或暂停当前回合。是否立刻参与由当前玩法的安全参与点决定。
- 房主在回合中请求切换桌台时，该请求排队；当前回合完成结算并暂停新下注后再切换。
- 应用层必须区分“玩法/规则配置切换”和“物理桌面/房间切换”。目标使用同一桌型、座位、下注面、设备和房间时，只替换规则会话、配置和表现 UI；目标物理布局不同才加载新桌或房间。
- 手绘脸属于 appearance data，不属于规则状态。第一版只保存一张固定画布的当前脸，可存为压缩贴图或绘制数据；不得让头像贴图、绘制工具或安全过滤进入 Core/Blackjack 规则程序集。
- 官方游戏内筹码余额不设产品层面的硬封顶；下注上限属于桌面或玩法变体配置，不存在全局最大下注。
- 赌场/系统可以向玩家提供个人信用额度或救济，但必须作为系统来源的账本交易处理，不得实现为玩家间借贷或通用转账。
- 系统信用 v0.1 使用 0-100 信用度、以每日基础补给量 `D` 为单位的分档额度、7 天信用周期、按总欠款每日复利、逾期扣 20 信用度、以及每月一次赌场宽限；`D` 的具体筹码值仍待经济调参决定。
- 信用状态不得作为玩法、桌台或外观/非玩法消费的准入门槛；它只影响信用系统内部的额度、还款、信用度、提示和账本展示。
- 第一可玩 MVP 冻结为本地二十一点竖切：本地状态机、本地账本/档案、灰盒 UI、基础庄家/AI、自动测试和本地模拟。Host/Client 联机、赌场外壳、落座 CG、头像绘制实现、第二玩法和完整长期系统推迟到后续里程碑。
- 初始目标平台是 Windows PC；具体互联网传输/中继方案仍待定。

## 1. 架构目标

项目采用“规则与表现分离、房主权威、玩法模块化”的结构。第一阶段只构建二十一点纯 C# 核心，后续再接入 Unity 画面、AI、存档和好友联机。

核心原则：

- 牌局结果由规则层产生，动画只展示结果。
- 单人模式与好友模式运行同一套规则核心。
- 当前权威端是房主主机，未来即使更换网络承载也不重写玩法规则。
- 新玩法复用账户、筹码、座位、房间、回合、日志与网络协议框架。
- 所有规则核心都能脱离场景和 MonoBehaviour 运行自动测试。

## 2. 分层结构

```text

└── Recovery checkpoint

Casino.Networking
├── Host/Client adapter
├── Commands and snapshots
├── Reconnect

Casino.Presentation
├── UI presenters
├── Card and chip views
├── Dealer and player animation
├── Seated camera

```

Dependency direction must point inward:

```text
Presentation ─┐
Networking ───┼→ Application → Blackjack → Core
Persistence ──┘
```

`Core` and `Blackjack` cannot reference Unity, UI, transport, scene objects, file APIs, or cloud services.

## 4. Authoritative data flow

```text
Local input
→ Client command
→ Host validates party, table, round, player, hand, action and balance
→ Pure C# game session applies command
→ Authoritative state and domain events are produced
→ Host broadcasts confirmed snapshot/events
→ Each client updates UI and plays animation
→ Confirmed settlement is written to the local ledger
```

Clients never submit a card result, random seed, final balance, or declared win. They submit intentions such as `PlaceBet`, `Hit`, `Stand`, `Double`, `Split`, and `BuyInsurance`.

## 5. Rule state versus presentation state

Rule state contains only serializable game facts:

- party identifier, table identifier, and game identifier when needed by the application layer
- round identifier and phase
- seat occupancy and control source
- bets and balances
- visible cards and hidden-card markers
- current acting seat and hand
- legal actions and deadlines
- completed settlement records

Appearance state contains local/profile data that may be synchronized by the application layer but never affects rules:

- selected card-head or chip-head type
- one current fixed-canvas face texture or drawing data
- local preference to replace other players' custom faces with a default face

Presentation state contains local-only details:

- camera yaw and pitch
- current animation time
- highlighted button
- particle, sound, and haptic feedback
- whether the player skipped a cinematic

Local presentation state is never used to validate an action or calculate a result.

## 6. Randomness

Rules depend on an `IRandomSource` abstraction.

- Production Host uses a system-backed random source to shuffle the shoe.
- Tests use scripted or seeded sources for exact reproduction.
- Fisher–Yates shuffle is implemented once in Core.
- The Host owns the real shoe and does not send the dealer hole card before reveal.
- The current friends-only trust model does not claim protection against a malicious Host.

## 7. Chips and settlement

- Use integer chip units only.
- Table configuration must keep 3:2 blackjack payouts exactly representable.
- Table or variant configuration owns minimum bets, maximum bets, and any explicit no-limit/all-in mode; Core must not depend on a global maximum bet.
- Official chip balances have no product-level hard cap, but storage and arithmetic must use safe integer bounds and overflow checks.
- Bets are reserved during a round and committed once through a settlement record.
- Every round, action, and ledger transaction has a stable unique identifier.
- Casino/system credit or relief is a ledger transaction from a system source to one player, never a player-to-player loan or generic transfer.
- Outstanding credit debt must not be exposed to game modules as a content-access gate. Game modules may validate available balance and table limits, while credit score, debt, repayment, and warning UI stay in economy/persistence/application services.
- Reapplying a confirmed settlement must produce no additional balance change.
- Local saves retain the latest confirmed round and balance checkpoint.

### 7.1 Casino/system credit service

- Store available official-chip balance separately from credit debt. Available balance must not become negative because of credit debt.
- Store credit score, current total debt, credit cycle identifier, opened time, due time, last interest settlement date, overdue-penalty-applied flag, and the last month in which casino forgiveness was used.
- Credit score is clamped to 0-100. New profiles start at 60. The first daily check-in can add +1 credit score up to 100.
- Borrowing limit uses the configured daily base supply amount `D`: 0-19 credit = 0, 20-39 = 3D, 40-59 = 6D, 60-79 = 10D, and 80-100 = 15D.
- Borrowing creates a system-source ledger transaction and increases both available balance and total debt. Borrowing is valid only up to remaining credit, where remaining credit is max borrowing minus current total debt, floored at 0.
- All borrowed amounts share one debt pool and one due date. Additional borrowing must not create a separate debt instrument or refresh the due date.
- Daily interest settlement must be idempotent with a stable key such as profile, credit cycle, and settlement date. Interest is calculated on total debt and rounded up to integer chip units.
- Interest tiers are 1%, 3%, 6%, and 10% per day for debt ratios 0-25%, >25-50%, >50-75%, and >75%/over-limit. If max borrowing is 0 while debt remains, use the 10% tier.
- Repayment creates ledger transactions against the same debt pool. Manual repayment can use any positive amount up to available balance and current debt.
- While debt exists, positive official-chip income routes 50% to automatic repayment before the rest enters available balance. Credit issue transactions do not trigger this automatic repayment.
- At due time, if debt remains, apply one idempotent -20 credit-score penalty for that credit cycle. Overdue debt continues with the 10% daily interest tier and disables new borrowing only.
- Monthly casino forgiveness is an idempotent system transaction available once per calendar month outside active rounds and settlements. It clears current debt, blocks new borrowing for the rest of that month, and sets credit score to `min(max(currentCredit - 30, 20), 40)`.
- Credit UI must show current score, limit, requested borrowing, post-borrowing debt, current daily interest tier, projected 7-day debt, due time, overdue penalty, monthly forgiveness availability, and a no-real-money notice before confirmation.

## 8. Persistence

The first implementation stores a versioned JSON profile beneath Unity's persistent data directory.

Safe-write sequence:

1. Serialize and validate the new profile.
2. Write a temporary file.
3. Flush and replace the previous primary file.
4. Retain one last-known-good backup.

Checksums can detect accidental corruption, but local saves cannot be made cheat-proof without a trusted account server. That limitation is accepted for the current scope.

## 9. Networking boundary

The application layer talks to an `IGameSessionTransport`, not directly to a specific networking package.

Current responsibilities:

- Party creator starts as Host.
- Friends join the persistent party through an invite or join code.
- The party supports up to six human players. AI fills table seats but does not consume party slots.
- Host validates all commands and runs AI.
- Disconnecting players are temporarily controlled by ordinary AI.
- Host loss closes the room; there is no host migration.
- Game or rules switching preserves party membership, Host, connections, appearance data, and confirmed official chip balances, but discards current-game temporary state after safe settlement.
- If the next game or variant uses the same physical table layout, the application swaps the active rules session and table UI in place. If the layout, equipment, betting surface, or room differs, it performs a queued table or room transition.
- A relay may forward internet traffic, but it does not become the gameplay authority.

Transport integration begins only after the local round state machine and tests are stable.

## 10. Presentation boundary

- Card, chip, dealer, and camera objects subscribe to confirmed domain events.
- Object pooling is used for frequently dealt cards and chips.
- A seating Timeline controls the camera until the seated marker fires.
- After seating, camera position is locked while local yaw and pitch are enabled.
- Critical action UI remains visible regardless of look direction, with a recenter action toward the table.
- Animation completion may unblock presentation queues but cannot advance game rules.

## 11. Testing strategy

### Edit mode

- card values and multiple aces
- soft and hard hands
- natural blackjack versus split 21
- split eligibility for ten-value ranks
- S17 dealer behavior
- double, split, and insurance legality
- normal, blackjack, push, bust, and insurance payouts
- duplicate command and duplicate settlement protection
- deterministic shoe order

### Play mode

- presenter consumes events in order
- UI exposes only legal actions
- seating cinematic hands control to seated camera
- reconnect snapshot rebuilds visible state
- timeout changes control source to AI

### Simulation

Run large batches without Unity scene objects to detect state deadlocks, invalid balances, impossible cards, or suspicious probability distribution.

## 12. Implementation order

1. Core value types, random source, shoe, and hand evaluator.
2. Blackjack legal actions, dealer rules, and settlement.
3. Local round state machine and deterministic tests.
4. Greybox table, UI presenter, and seated camera.
5. AI players and local chip ledger.
6. Local simulation and first playable MVP hardening.
7. Host/Client adapter, reconnect, and timeout takeover.
8. Compact card room, seating cinematic, sound, and final art.

Do not start a later layer to compensate for an unfinished or untested earlier layer.
